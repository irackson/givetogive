# GiveToGive production mail runtime and SQL receipt admission

This candidate completes the runtime/store seam and stable issuer-to-mail intent. It keeps legacy provider selection by default and preserves staging encrypted capture/recipient restrictions before the sender path. Financial flags, Stripe/payment/simulation state and the paused financial Goal remain untouched.

Admission requires `GIVE_MAIL_RUNTIME_ADMISSION=v1`, `GIVE_MAIL_STORAGE_ADMISSION=v1`, exact `APP_ENV=production`, `NODE_ENV=production`, `VERCEL_ENV=production`, `GIVE_AUTH_ORIGIN=https://givetogive.ianrackson.com`, `GIVE_MAIL_RECEIPT_MAX_RECORDS` canonical integer1..10000, canonical-base64 `GIVE_MAIL_BINDING_KEY_B64` decoded32..256bytes and the existing explicit GiveToGive/US Mailgun sender fields. Construction creates no DB connection or native state and sends nothing. Invalid explicit selection never falls back. Repeated calls reread admission rather than retain stale configuration in a runtime cache.

The normal issuer still creates/rotates the same random token with its existing transaction, expiry, consumption and rate limits. The send path receives the hash of that already persisted high-entropy token and derives a purpose-separated private HMAC intent. It never invents an intent for a legacy caller lacking a token hash/intent, never stores token/link/email/body in the mail ledger, and never changes a failed/unknown claim into a new send. Verification and reset purposes, distinct tokens and conflicting payloads remain separate. An explicit later issuance is an existing user-requested token lifecycle, not a retry of an ambiguous message.

The mail-only origin helper changes verification/reset-link origin only during explicit production Mailgun admission. `APP_URL`/payment/webhook/staging destinations are not rewritten. Unadmitted/default and staging link construction retains the existing APP_URL/VERCEL_PROJECT_PRODUCTION_URL/NEXTAUTH_URL precedence. Keep existing signed links/callbacks/cookies valid across the domain transition; do not globally redirect auth or provider routes.

## Native persistence proposal

`PostgresGiveMailReceiptStore` uses the existing application pool and a fixed, parameterized `public.give_mail_receipt_command_v1` invocation within one transaction. Server statement/lock timeouts are set to2seconds before the command. Adapter methods each invoke their captured executor once; no effect replay exists in the adapter. Transport remains bounded by its existing five-second total deadline. The existing pool's connection acquisition/commit may outlast that response deadline; an uncertain/late reservation may remain submitting, but cannot grant a late provider HTTP send or a retry. Hosted client/engine behavior, connection lifetime and native capacity need acceptance before activation.

`docs/sql/give-mail-receipts-v1.sql` is source only, never run by the application/build. It proposes an application-owned persistent singleton ledger table and SECURITY INVOKER validation/command functions, with no role/grant, trigger, financial/auth-table or existing-ledger migration. The command locks the control row before bounded full-history auditing and mutation. Exact schema/capacity/used count, request/claim/phase/outcome shapes, all accepted provider IDs and both directions of their map must agree. Every new reservation is recorded submitting before HTTP. Terminal outcomes are immutable; claim mismatch is stale, duplicate payload conflict held, provider-ID collision becomes permanent unknown. One UPDATE stores a validated state; transaction errors roll it back. No TTL, deletion, rearm, missing-state creation or restore inference exists.

No production table/control/function has been installed.
